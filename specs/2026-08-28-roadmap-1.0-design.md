# depin 1.0 roadmap — design

Date: 2026-08-28
Baseline: 0.4.3
Status: approved, pending implementation plan

## Goal

Take depin from 0.4.3 to a library a range of unrelated projects can depend on:
complete in features, verified beyond line coverage, supported across the Python
versions those projects actually run, its consumer-visible types and its
performance both measured rather than asserted, and its surface settled behind a
stated stability commitment.

Everything that touches the public surface lands before the freeze. Nothing
required for 1.0 is deferred to "post-1.0".

**1.0 itself is undated.** Steps 6 through 8 make it possible; none of them
obliges it. A version number is a support commitment, and the project takes it
when it chooses to rather than because a roadmap reached its last row. Step 9
holds what would remain at that point, and holds nothing else.

## Baseline

Measured on 2026-08-28 at commit `fa39c39`:

- 271 tests, 97.91% coverage over `depin/` against a 95% floor.
- `basedpyright --strict` clean; no `# type: ignore`, `# pyright: ignore`, or
  `typing.cast` in the package.
- CI on Python 3.12–3.14 across Linux, macOS, and Windows, plus a
  `lowest-direct` resolution job, CodeQL, dependency review, and a clean-env
  wheel smoke test.
- Versioned documentation site; releases published by Trusted Publishing.
- One integration: `depin.ext.fastapi`.

The gap to 1.0 is reach and proof, not repair.

## Decisions taken

| Decision | Choice | Rationale |
| --- | --- | --- |
| Roadmap horizon | Ends at 1.0 | A closed set of milestones with a defined terminus, rather than an open sequence. |
| Python floor | 3.12, unchanged | PEP 695 syntax appears roughly 49 times across `depin/`, and `AGENTS.md` mandates it. Lowering the floor means rewriting every generic to `TypeVar` and revoking a project rule. 3.11 leaves support in October 2027. Reach is extended upward instead. |
| Framework support | Public contract plus a curated set | A documented, versioned integration protocol lets third parties ship integrations without depending on internals. depin ships one integration per hosting shape and carries no more maintenance surface than that. |
| Performance | Measure first, optimise on evidence | A baseline and a regression gate land before the feature work, so no step degrades what the README advertises. Compiling the plan into per-key closures happens only if the baseline shows it matters. |
| Lazy injection | Excluded | Its primary use is breaking cycles, which depin rejects by design; its secondary use, deferring expensive construction, is already the default singleton behaviour. |

## Cross-cutting requirements

Every step satisfies all of the following before it is considered done. They
are not repeated in the step sections.

- The five gates pass with no warnings or waivers: `ruff format`, `ruff check`,
  `basedpyright`, `mypy`, `pytest`.
- `mkdocs build --strict` passes, and the narrative guide covers any new
  concept.
- Public API additions carry Google-style docstrings with a doctest `Example:`,
  per `AGENTS.md`.
- A runnable program in `examples/`, listed in `examples/README.md` and
  exercised by `tests/integration/test_examples.py`, for any user-facing
  concept.
- No regression against the benchmark baseline established in Step 0.
- Every new feature is exercised through `depin.ext.fastapi` before it is
  considered complete. The existing integration is the design-validation
  vehicle, not a late consumer.

## Step 0 — Support matrix and safety net (0.5.0)

**Objective.** Establish the ground truth every later step is measured against.
No public surface changes.

**Deliverables.**

- Extend the CI matrix with free-threaded CPython builds (3.13t, 3.14t), and
  with the current 3.15 pre-release in a failure-tolerant job. depin advertises that
  a singleton is constructed exactly once under contention; without the GIL that
  guarantee stops being subsidised by the interpreter and rests entirely on the
  library's own locks. Verifying it is a precondition of the 1.0 claim, not an
  optional extra.
- Run the concurrency and thread-safety suites under real thread parallelism on
  the free-threaded builds.
- Type-check against every version in the matrix. `[tool.basedpyright]` pins
  `pythonVersion = "3.12"` while CI tests up to 3.14.
- Add `mypy --strict` to the `dev` group and to CI, alongside a type-conformance
  suite using `assert_type` over `resolve`, `__getitem__`, `injected`, `inject`,
  `Inject[T]`, `Token[T]`, and `override`. The README claim of no `# type:
  ignore` at call sites must hold under two checkers before it becomes a 1.0
  commitment.
- Add a `ty` job run through `uvx`, advisory only (`continue-on-error: true`):
  `ty` is on `0.0.x` versioning with no stable API, so it gives advance signal
  from a second, independently-implemented checker without being able to block
  a merge on a diagnostic that may not exist in the next release.
- Add `benchmarks/` with a CI regression gate. Scenarios: `freeze()` over graphs
  of 10, 100, and 1000 nodes; cached singleton resolution; transient chain
  resolution; scope open and close; a call through an `@inject` wrapper;
  `aresolve`.
- Publish a version-support policy on the SPEC 0 model: which versions are
  supported, when they are dropped, and what triggers removal.
- Add signed build provenance to the publish workflow, an SBOM artifact, and an
  OpenSSF Scorecard badge.

**Acceptance criteria.**

- CI is green on 3.12, 3.13, 3.14, 3.13t, and 3.14t.
- The thread-safety suite fails when its lock is removed, on a free-threaded
  build.
- `mypy --strict` and `basedpyright --strict` both report zero diagnostics.
- The benchmark gate measures the base branch and the head branch on the same
  runner in the same job, and fails on a seeded regression. No baseline is
  committed to the repository: one measured on a different machine would compare
  hardware rather than code.

## Carried from Step 0

Findings surfaced during Step 0 and routed to the step that owns them, rather
than fixed in place.

- **Concurrency test weakness (Step 1).**
  `tests/unit/test_free_threading.py::test_the_per_key_lock_table_survives_concurrent_creation`
  detects a removed `ScopeFrame._mutex` guard in roughly 16 of 20 runs on a
  free-threaded 3.13 build, not consistently. `AGENTS.md` requires a
  concurrency test to fail when its guard is removed; this one fails
  probabilistically. The companion test covering the same lock through the
  singleton resolution path, `test_a_singleton_is_built_once_with_no_gil`, was
  measured at 20 of 20 with no false failures, so the invariant is guarded
  overall — the direct test of `sync_lock_for` is the weak one. Widening the
  detection window by moving the synchronisation barrier earlier was tried and
  made detection worse. Step 1 owns concurrency stress and should replace the
  barrier with a fault-injection rendezvous inside `sync_lock_for`'s
  read-then-write step, forcing every thread into the critical section
  deterministically without a sleep.
- **`type-abstract` on `provides` (Step 3).** Moved from the freeze: it is a
  public signature change, so it belongs with the rest of Step 3's
  resolution-semantics work rather than in the last window before 1.0. See
  that step's `provides` signature deliverable. The limitation is documented
  for users in `docs/support-policy.md` in the meantime.
- **Cubic failing-freeze path (Step 7).** Step 0 made the passing path of
  `Container.freeze()` linear, but its failing path is still cubic:
  `_check_missing` still walks from every root with `_collect_missing` once
  `_any_unsatisfied` reports something missing, and `_collect_missing`
  recomputes its chain-identity set from the current chain on every stack pop
  rather than carrying and extending one. Measured at 188 ms for 200 nodes and
  1386 ms for 400 nodes — 2x the nodes for 7.4x the time. A 1000-provider graph
  with one unsatisfied dependency still costs roughly the 20 seconds the fix
  removed from the passing path. For a library whose central claim is
  build-time validation, the failing freeze is the common case during
  development, and no benchmark in `benchmarks/` covers the error path, so the
  regression gate would not catch a change there either. The cheap fix,
  alongside the optimisation work already scheduled in Step 7, is to carry the
  frozenset of chain identities on the stack entry and extend it on push,
  removing one factor of n.

## Step 1 — Verification depth (0.6.0)

**Objective.** Prove the suite's strength, not just its reach. Line coverage
measures executed statements; a library many projects depend on needs more.

**Deliverables.**

- Property-based tests over the graph validator with Hypothesis, generating
  random provider graphs. Invariants: `freeze()` either raises a `DepinError` or
  returns a valid topological order; no code path escapes the `DepinError`
  hierarchy; an acyclic graph never raises `CircularDependencyError`; a graph
  with no singleton-to-scoped edge never raises `CaptiveDependencyError`.
- Mutation testing over `depin/_core/` with a declared surviving-mutant
  threshold enforced in CI.
- Concurrency stress tests under free-threading, synchronised with explicit
  barriers and events. Timed sleeps remain forbidden.
- Teardown-under-failure tests: multiple simultaneous teardown failures, and a
  failure inside the drain itself, asserting that the `ExceptionGroup` preserves
  every failure and the reverse construction order.
- A free-threading assumption audit: an inventory of the places depin's
  correctness depends on interpreter behaviour that is not true without the
  GIL. Step 0 found one such site only by accident: `gc.get_objects()` stops
  enumerating heap types once any thread has run on a free-threaded build, and
  calling `gc.collect()` does not bring them back, which left the
  missing-provider suggestion in `MissingProviderError` silently
  non-functional on exactly the applications free-threading exists to serve.
  This deliverable looks for the rest deliberately: the `contextvars`
  semantics scope isolation depends on, the interaction between
  `ScopeFrame`'s `threading.Lock` and `asyncio.Lock`, and every place the code
  assumes a `dict` or `list` operation is atomic. Each site produces a
  recorded finding — either the assumption holds, or a test that pins it.

**Acceptance criteria.**

- The mutation threshold is enforced and documented.
- Every property test is shown to fail against a deliberately broken validator.

**Risk.** Mutation testing is slow. Mitigation: run it on a schedule and on
changes under `depin/_core/`, not on every pull request.

## Step 2 — Graph diagnostics (0.7.0)

**Objective.** Make the validated graph inspectable. The data already exists in
`ResolutionPlan`; exposing it makes every later step debuggable by construction
and is the most direct demonstration of the build-time validation thesis.

**Deliverables.**

- `FrozenContainer.explain(key) -> str`: the resolution tree for a key, showing
  scope, provider shape, and tag per node.
- `FrozenContainer.graph()`: an immutable, navigable view of the plan, with
  `dot` and `mermaid` export.

**Acceptance criteria.**

- `explain()` output for a missing key names the same chain the corresponding
  `MissingProviderError` names.
- Export output is deterministic across runs, so it is diffable in a test.

## Carried from Step 2

Findings surfaced during Step 2 and routed to the step that owns them, rather
than fixed in place.

- **Elision benchmark does not elide (Step 7).** `benchmarks/test_diagnostics.py`
  times `explain()` over `build_chain(1000)`, and `benchmarks/graphs.py` builds a
  strictly linear chain, so no node is ever reached twice and the
  subtree-elision guard never fires. A regression that removed the guard would
  leave this benchmark green, because per-path expansion only blows up on a
  diamond. The behaviour is covered by `test_a_repeated_subtree_is_rendered_once`;
  the regression guard the design claims is what is missing. Step 7 owns
  adding a layered-DAG generator and benchmarking `explain()` over it.
- **Chain divergence on a bound-and-defaulted intermediate (Step 3).**
  `_collect_missing` in `depin/_core/graph.py` skips a parameter carrying a
  default, including for traversal, while `_deepest_requirement` in
  `depin/_core/render.py` traverses every satisfied edge. When an intermediate
  parameter is both bound and defaulted, the two report chains of different
  length — the freeze error names `B -> C` where `explain()` names
  `A -> B -> C`. The wording and the owner agree; only the chain differs, and
  `explain()`'s is the more informative one. Closing it means making
  `_collect_missing` traverse bound-defaulted parameters, which changes
  existing error text and so belongs with deliberate work on resolution
  semantics rather than here. That work is Step 3, and specifically its second
  cycle, which is the one that redefines what a parameter with a default means.
  The finding was first labelled (Step 8); the label was wrong, and its own text
  said so.
- **Exponential missing-key walk (Step 7).** `_deepest_requirement` enumerates
  every simple path from every node with no memoisation. Measured on a
  fan-in-2 DAG: 0.007 s at 14 nodes, 0.033 s at 18, 0.081 s at 20, 0.210 s at
  22 — roughly 2.6x per two nodes. `_collect_missing` already has the same
  shape on `main` (0.327 s at 22 nodes), so this mirrors the cubic
  failing-freeze path Step 0 already routed to Step 7. The longest chain to a
  node is a dynamic program over a DAG in O(V+E); solving it once would serve
  both walks.

## Step 3 — Resolution semantics (0.8.0, 0.9.0, 0.10.0)

**Objective.** Close the resolution-model gaps against consolidated DI systems.
This is the highest-risk step: three of its five deliverables change what
`freeze()` accepts, and the resolution model is what every later step composes
against.

Step 3 ships as three releases rather than one. Shipping five interacting
changes to the resolution model in a single release makes the release the unit
of diagnosis: a regression reported against it names five candidates, and the
one deliverable that touches no validation rule cannot be released ahead of the
three that do. The split groups by what each deliverable changes, not by size.

| Cycle | Version | Deliverables | Why together |
| --- | --- | --- | --- |
| 1 | 0.8.0 | `provides` signature, aliasing | Neither changes a validation rule. `provides` is a repair to a public signature; an alias is an ordinary node on an ordinary edge. |
| 2 | 0.9.0 | Optional dependencies, collection injection | Both change what an unsatisfied parameter means. Both pass through `ParamSpec`, `_any_unsatisfied`, and `_collect_missing`, so they cannot be validated apart. |
| 3 | 0.10.0 | Generic keys | Alone, because it is the one deliverable that redefines what a key is, and every validation rule reads a key. The premise this row first gave — that `resolve[T](key: type[T]) -> T` cannot express `Repo[User]` — was measured false by cycle 3's design spec: `Repo[User]` in expression position has the static type `type[Repo[User]]`, which solves `T` under both checkers, so the cycle needed no signature change at all. |

Each cycle carries its own design spec, implementation plan, pull request, and
release. Steps 4, 5, and 6 renumbered accordingly, to 0.11.0, 0.12.0, and 1.0.
Step 4 then split in turn, on the same grounds, which moved Step 5 to 0.13.0.
Step 5 split into four cycles on the same grounds, which spread it over
0.13.0–0.16.0 and left Step 7 at 1.0.

**Deliverables.**

- **Generic keys** *(cycle 3)*. `Repo[User]` as a provider key. Cycle 2 had
  already added `GenericAlias` to `ProviderKey` and admitted `list[X]` alone,
  for collection injection; `is_provider_key` rejected every other
  parameterised generic. Cycle 3 removes that restriction, requires a canonical
  spelling at every level of nesting, and adds rendering and registration.
- **Optional dependencies** *(cycle 2)*. A `T | None` parameter resolves to
  `None` when unbound, instead of failing at `freeze()`.
- **Collection injection** *(cycle 2)*. `list[Handler]` resolves every provider
  registered under the key, gated behind an explicit multi-binding registration
  so that `DuplicateProviderError` keeps firing on an accidental duplicate. The
  new feature must not silence the existing error.
- **Aliasing** *(cycle 1)*. `Container.alias(Store, to=PostgresStore)`: one
  instance reachable under two keys, without a second singleton.
- **`provides` signature** *(cycle 1)*. `@provides(SomeProtocol)` and
  `@provides(SomeABC)` make mypy report `type-abstract` at the decorator line,
  in the consumer's own file, at default settings; `basedpyright` does not. The
  cause is mechanical: mypy raises that error whenever a formal parameter is
  exactly `type[T]` with `T` a type variable — the same rule that made
  collapsing `FrozenContainer.__getitem__`'s overloads into a union signature
  fix the equivalent problem for `di[SomeProtocol]` during Step 0. The type
  parameter in `provides[A]` is phantom: `_ProvidesDecorator` is private and
  unexported, and `A` appears in no return type a consumer can observe. Three
  resolutions were on the table: erase `A`; make `A` load-bearing by binding the
  decorated class to it; or widen the parameter to a union and add a runtime
  guard rejecting non-classes. The second was measured and withdrawn — mypy
  rejects every class passed, including one that satisfies the target, and
  basedpyright rejects the declaration itself. Cycle 1 erases `A`. This is a
  public signature change, which is what this step is for, and it affects every
  mypy user who follows the pattern the README teaches — carrying it to the
  freeze would leave the papercut in five published releases.

**Acceptance criteria.**

- Each addition is validated at `freeze()`, not at resolution time, preserving
  the build-time guarantee.
- An accidental duplicate registration still raises `DuplicateProviderError`.
- A collection binding participates in captive-dependency validation like any
  other edge.

## Carried from Step 3

Findings surfaced during Step 3 and routed to the cycle that owns them, rather
than fixed in place.

- **Forward references to an alias key, a collection element, or a
  `scope_value` key (Step 3, cycle 3 — closed).** `_registered_classes` in
  `depin/_core/providers.py` builds the `localns` that resolves string
  annotations from records whose `source` is a class, so a key registered only
  through `alias`, only through `collect`'s `element` argument, or only
  through `scope_value` never enters it. A provider annotating that key as a
  string forward reference then fails at `freeze()` with "bind the class so
  depin can resolve the forward reference" — advice that would itself raise
  `DuplicateProviderError` when the key already has a binding elsewhere, and
  that is simply wrong when the key is a `Protocol` used only as a collection
  element, since callers do not bind a `Protocol` as its own provider. The
  defect is pre-existing: `scope_value` has the same hole on `main`, because a
  frame binding is not a class either. Aliasing and collection injection each
  widen the surface where it bites rather than introducing it, and cycle 2
  shipped without addressing it. Cycle 3 reopens `ProviderKey` handling and
  normalisation for generic keys — the same code region that builds and
  consults `localns` — and owns the fix: include alias, collection-element,
  and frame keys in the namespace the annotations resolve against, and stop
  telling the caller to bind a key that is a `Protocol`. Cycle 3 closed it.
  `_classes_reachable_from` now reads the whole record rather than its source
  alone — source, explicit `provides=`, frame key, alias key and target,
  collection element and members — and recurses into a generic key's
  arguments, so a class named only as `Repo[User]`'s parameter also enters the
  namespace. The advice was corrected in the same cycle, and the message a
  factory gets now distinguishes "no return annotation" from "return
  annotation present but unresolvable", which `get_type_hints` returning
  nothing on `NameError` had collapsed into one. Residue: the namespace is
  keyed by `__name__`, so two classes of the same name registered from
  different modules still collide, and a forward reference naming a class that
  appears in no record at all is still unresolvable — neither is new, and
  neither is routed forward.
- **Generated aliases and collections sit on real paths, in part (Step 3,
  cycle 2 — closed for the captive-path case).** `tests/unit/test_graph_properties.py`
  used to leave every generated alias key as a fresh class that no generated
  node depends on, so the alias was always a leaf the rest of the graph
  ignored, and the generative suite never placed an alias on a captive path,
  inside a cycle, or on an async-propagation path. Cycle 2 closed the
  captive-path case: `_materialize` now binds a fresh singleton consumer for
  every generated alias and collection (`_bind_consumer`), and
  `_has_singleton_to_scoped_path` folds their indices into `virtual_roots`, so
  a generated alias or collection that captures a scoped provider is now
  caught. The other two cases stay open: a generated alias or collection can
  still never land inside a cycle, because its consumer has exactly one
  outgoing edge and none back into it, so no generated case can loop through
  one, and the suite models no async dimension at all, for any node, so
  neither is ever exercised on an async-propagation path. Both remain covered
  only by their own single-shape tests —
  `test_a_cycle_through_an_alias_is_rejected` in
  `tests/unit/test_graph_validation.py`, and
  `test_an_alias_to_an_async_target_resolves_under_aresolve` and
  `test_an_alias_to_an_async_target_is_rejected_by_resolve` in
  `tests/unit/test_frozen_async.py`. Neither is a deliverable of any planned
  step, so neither is routed forward: both stand as an accepted limitation of
  the generative model.

## Step 4 — Composition and operations (0.11.0, 0.12.0)

**Objective.** Cover the behaviour-composition and lifecycle features that
production deployments need.

Step 4 ships as two releases rather than one, split by what each deliverable
does to the plan. Decoration and conditional activation both change what
`freeze()` produces — one rewrites a node, the other omits nodes — and both sit
between record collection and validation, so they cannot be validated apart.
Warmup and health checks read a plan that is already frozen and change nothing
in it, which is why they can follow without re-opening the construction path.

| Cycle | Version | Deliverables | Why together |
| --- | --- | --- | --- |
| 1 | 0.11.0 | Decoration, conditional activation | Both change what the `ResolutionPlan` contains, and each interacts with the other: a decorator over an inactive binding, an inactive binding required by an active one. |
| 2 | 0.12.0 | Eager warmup, health checks, the named-scopes decision | Both operate over a validated plan without altering it, and the decision is prose that has to land before the freeze. |

Each cycle carries its own design spec, implementation plan, pull request, and
release. Steps 5 and 6 renumber accordingly, to 0.13.0 and 1.0. Step 5 then
split in turn, over 0.13.0–0.16.0, leaving Step 8 at 1.0.

**Deliverables.**

- **Decoration** *(cycle 1)*. `Container.decorate(Store, wrapper)` wraps a
  resolved provider while preserving its scope and its position in teardown
  order. Covers logging, caching, and retry without inheritance.
- **Conditional activation** *(cycle 1)*. Bindings under a predicate, evaluated
  inside `freeze()` and never at resolution time, so the validated graph stays
  static.
- **Eager warmup** *(cycle 2)*. `di.warmup()` and `await di.awarmup()` construct
  every singleton at boot and return a report built on the Step 2 graph
  structure. A construction failure surfaces at startup rather than on the first
  request.
- **Health checks** *(cycle 2)*. A provider may declare a verification callable;
  `di.checks()` exposes them for readiness endpoints.
- **Custom named scopes** *(cycle 2)*. Rejected: neither Step 3 nor Step 4
  surfaced a use case the three fixed scopes cannot express. Decoration was the
  one place a fourth lifetime could plausibly have been needed, and it was
  measured not to be — a decorated singleton is two singleton nodes, not a new
  lifetime. Full reasoning in
  `specs/2026-08-31-step-4-warmup-health-design.md`'s "Custom named scopes —
  rejected" section.

**Acceptance criteria.**

- A decorated provider is torn down exactly once, in the position its
  undecorated form would have occupied.
- Conditional bindings that are inactive do not appear in the plan and are not
  validated as dependencies.
- `warmup()` on a graph containing an async provider raises rather than blocking
  an event loop, matching the existing `resolve` / `aresolve` rule.

## Carried from Step 4

Findings surfaced during Step 4 and routed to the cycle or step that owns them,
rather than fixed in place.

- **A captive-dependency message does not name the decorator that owns the
  offending edge (Step 8).** `Container.decorate` gives each wrapper a node
  under the decorated key, so a wrapper whose own dependency is scoped, over a
  singleton binding, is reported as `captive dependency: singleton Store
  depends on scoped Session (chain: Store -> Session)`. The message is true —
  `Store` is the key the wrapper occupies — but the binding the user wrote
  under that name has no `Session` parameter, and nothing in the chain says a
  decorator introduced the edge. Naming it means reshaping `_format_captive`,
  which every captive path shares, so the fix belongs to a step that owns
  diagnostics rather than to the cycle that surfaced it. Step 8's surface
  review is where every message is read against what it promises.

- **No public way to render a `ProviderKey` (Step 8).** `GraphNode.key`,
  `HealthCheck.key`, and `HealthResult.key` are all `ProviderKey`, a union, and
  the only renderer is `depin._core.spec.fmt_key`, which is private. Every
  consumer that prints a key therefore writes its own `isinstance(key, type)`
  narrowing; cycle 2 added three such helpers, in two examples and one
  integration test. The gap is not new — Step 2 exposed `GraphNode.key` — but
  each report added since has widened it. Step 8's surface review, which
  justifies every symbol in `__all__`, is where a public renderer is decided.

- **The mutation gate's own suite was flaky under its two-second timeout
  (Step 8).** `[tool.mutmut] pytest_add_cli_args` sets `--timeout=2`, and two
  property-based modules — `tests/unit/test_graph_properties.py` and
  `tests/unit/test_graph_render.py` — exceeded it reproducibly on an unmutated
  tree under load. The CI job tolerated it because a timeout on the baseline
  run does not by itself fail the threshold, but it made a local scoped run
  unreliable and inflated the survivor count non-deterministically. Step 5
  cycle 2 applied the fix once the flakiness stopped a release: both modules
  now carry `pytestmark = pytest.mark.timeout(15)`, which `pytest-timeout`
  honours over the command-line value. What remains for Step 8 is not the
  timeout itself but whether these property modules should be faster rather
  than merely permitted to be slow.

- **`depin/_core` carried 90 mutation survivors that predate Step 4 — cleared
  in Step 5.** The gate is a whole-package percentage, and Step 4 cycle 2's two
  new modules pushed it under the floor at 94.3% until their own 45 survivors
  were killed. The remainder sat in `typeguards` (27), `providers` (14),
  `overrides` (6), `markers` (3), `introspect` (3), `graph` (2), `construct`
  (2), and `render` (1), and every one of them was `main`'s rather than any
  step's. They were the margin the threshold ran on: the next module added
  without exhaustive message assertions would fail the gate again — which is
  exactly what happened, twice, before the backlog was paid down.

  **Measured truthfully for the first time in Step 5, cycle 2.** The count above
  was inflated in depin's favour. `[tool.mutmut] pytest_add_cli_args` passes
  `--timeout=2`, and the two Hypothesis property modules exceeded it — a test
  that pytest-timeout kills *fails*, and a failing test is what mutmut reads as
  a killed mutant, so every mutant those modules would otherwise have let live
  was scored as dead. Giving the modules a realistic per-module timeout, which
  cycle 2 did because the flakiness had begun aborting the gate outright,
  removed the inflation and produced the first honest score: **93.7%, 2262
  killed and 151 survived of 2413**, against a 95% floor. The survivors sat in
  `providers` (55), `decoration` (27), `typeguards` (26), `overrides` (6),
  `graph` (5), `markers` (3), `introspect` (3), `construct` (2), `spec` (1) and
  `render` (1) — none in `scope` or `frozen`, the modules cycle 2 added to, so
  this was Steps 3 and 4's backlog seen without the distortion.

  **Paid down before Step 5 cycle 3, in its own pull request.** The floor needed
  31 mutants dead; 96 died. Forty tests pin the error messages of `typeguards`
  (26 survivors to 0), `decoration` (27 to 5) and `providers` (54 to 7) as
  complete strings compared with `==`, which is the assertion style the survivors
  existed to demand. No source file changed, no configuration moved, and no
  suppression was added. CI went from 93.7% to **97.7% — 2358 killed and 55
  survived of 2413**. The twelve survivors left alive are equivalent mutants,
  two of them verified by reading the code rather than argued.

  What Step 8 still owns is not this backlog but the residue recorded under
  *Carried from Step 5*: the gate continues to flatter `frozen` and `scope`,
  because their tests exceed mutmut's two-second timeout on CI and a timed-out
  test reads as a dead mutant.

## Step 5 — Integration contract and ecosystem (0.13.0, 0.14.0, 0.15.0, 0.16.0)

**Shipped, all four cycles.** 0.13.0 the contract, 0.14.0 the pytest plugin and
singleton eviction, 0.15.0 Starlette/Litestar/Flask, 0.16.0 Click/Typer/Taskiq.
`depin/ext/` holds eleven modules and the distribution declares eight extras.

**Objective.** Extend reach without extending maintenance surface
proportionally. The feature surface is stable by this point, so integrations
consume it without risk of rewrite.

Step 5 ships as four releases rather than one. The criterion is the region of
the tree each cycle changes, taken in dependency order, so that a regression
reported against a release names one region: cycle 1 is the only one that
changes the resolution path, cycle 2 the only remaining one that changes
`depin/_core` at all, and cycles 3 and 4 add nothing outside `depin/ext/` and
`[project.optional-dependencies]`. Cycles 3 and 4 then split the six curated
integrations by hosting shape rather than by count, because the two groups
differ in how the framework hands control over: a request/response host wraps
the unit of work in a block, while a command or message host exposes a pair of
hooks.

| Cycle | Version | Deliverables | Why together |
| --- | --- | --- | --- |
| 1 | 0.13.0 | The integration contract, `depin.ext.fastapi` rewritten on it, contract tests, the "writing an integration" guide, and the two-sided version matrix | The contract and its proof cannot be split: the rewrite is what shows the contract is sufficient rather than aspirational, and the guide is the contract's normative prose. The only cycle that changes the resolution path. |
| 2 | 0.14.0 | The `pytest` plugin and the singleton-cache eviction it needs | Eviction is a runtime change with teardown consequences, and the plugin is its only consumer. Together they remove the "overrides do not evict caches" caveat; apart, one ships a seam with no user and the other a plugin that cannot keep its promise. |
| 3 | 0.15.0 | Starlette, Flask, Litestar | The request/response hosts. Starlette and Litestar share one ASGI middleware with the FastAPI integration cycle 1 rewrote; Flask is its WSGI counterpart. All three seed one framework object into one scope per request. |
| 4 | 0.16.0 | Click/Typer, Taskiq | The command and message hosts. Neither has a request, both open a scope per invocation or per message, and both expose lifecycle hooks as a pair rather than as a block — the case the contract's context managers are entered and exited by hand. |

Each cycle carries its own design spec, implementation plan, pull request, and
release. Step 8 remains 1.0.

**Deliverables.**

- **A public, versioned integration protocol** *(cycle 1)*: the seam
  `RequestScope` already uses, extracted, documented, and covered by contract
  tests. Third parties write integrations against it without touching
  `depin._core`.
- **A curated set shipped in the repository** *(cycles 2, 3, 4)*: `pytest`,
  Starlette, Flask, Litestar, Click/Typer, and Taskiq. This covers ASGI, WSGI,
  CLI, and worker processes — the four shapes in which a Python project hosts a
  container.
- **A `pytest` plugin with an evicting override mode** *(cycle 2)*: it drops the
  singleton cache for the duration of the block, removing the "overrides do not
  evict caches" caveat currently documented in the README.
- **A "writing an integration" guide** *(cycle 1)*, with the contract as its
  normative reference.
- **Each integration tested against both its declared minimum and the current
  release of its framework** *(cycle 1 builds the matrix; every later cycle
  extends it)*. Every integration is an optional extra with a declared floor,
  so the existing `minimum-versions` job covers the floor and a new
  `latest-versions` job covers the current release. Two jobs total, for any
  number of integrations, rather than two jobs per integration.

**Acceptance criteria.**

- `depin.ext.fastapi` is rewritten on top of the public contract, proving the
  contract is sufficient rather than aspirational *(cycle 1)*.
- Contract tests fail if an integration reaches into `depin._core` *(cycle 1,
  extended by every later cycle to the integrations it adds)*.

**Risk.** Six integrations is the largest step by volume, and each is a standing
upstream-breakage vector. Mitigation: the contract absorbs depin-side change, and
each integration stays thin enough that a framework release breaks configuration,
not logic.

## Carried from Step 5

Findings surfaced during Step 5 and routed to the cycle or step that owns them,
rather than fixed in place.

- **Two containers cannot nest their scopes (Step 8).**
  `FrozenContainer.scope()` pushes onto one process-wide `ContextVar` in
  `depin/_core/scope.py`, and `ScopeFrame.claim_cached` walks the parent chain
  keyed on `(key, tag)` alone, so a second container's scope opened inside a
  first one's becomes a child of the first frame and resolves a shared key to
  the first container's cached instance — the second container's own binding
  never runs. Cycle 1 documented the limitation in `Host` and in
  `docs/guide/integrations.md` and pinned it with a test rather than changing
  the frame cache, because keying the cache by container identity changes the
  core resolution path in the release whose job was to prove the contract
  sufficient. Step 8 owns deciding whether 1.0 ships the limitation documented
  or the cache keyed.

- **A tagged `scope_value` reads the untagged frame slot (Step 8).**
  `Container.scope_value` accepts `tag=`, but `ScopeFrame.provide` has no tag
  and `FrozenContainer._read_frame` reads the bare key, so two tagged
  `scope_value` declarations of one key read the same slot. The mismatch
  predates this step, but cycle 1 freezes seeding as a contract operation,
  which turns it from an implementation detail into a question about the public
  surface. Step 8's surface review owns it.

- **`provides=` cannot name a `Token` key (Step 6).** `provides` is typed
  `type[object] | None` across all seven `bind` overloads in
  `depin/_core/bindings.py`, while `ProviderKey` — the type the plan actually
  accepts — includes `Token`. Binding a factory under a `Token` key therefore
  runs correctly and is rejected by both checkers:

  ```python
  port = Token[int]('port')
  di = Container().bind(make_port, provides=port).freeze()
  ```

  The program resolves and prints `resolved 8080`; `basedpyright` reports
  `"Token[int]" is not assignable to "None"`, and `mypy` reports no matching
  overload. `Container.value` covers a constant under a `Token` and nothing
  covers a factory, so the only route is a suppression at the call site — the
  same papercut Step 3 cycle 1 pulled forward for `provides` and
  `type-abstract`, against a README whose headline claim is that a user needs
  no `# type: ignore` at a call site. Widening the parameter touches all seven
  overloads and the key handling in `depin/_core/providers.py`, which is
  resolution-semantics work in the release whose job was to prove the contract
  sufficient, so cycle 1's review round surfaced it and cycle 1 does not fix
  it. **Step 6 owns it**, as a signature repair rather than a documentation
  note: a call that runs correctly and that both checkers reject is precisely
  what the consumer typing contract exists to catch, and it should be repaired
  by the step that builds the corpus which would have caught it.

- **Atomicity guards are only provable with fault injection (Step 8).**
  `ScopeFrame._take_all` must clear the cache and take the teardown list under
  one lock, and no test can distinguish that from two lock regions without
  instrumenting the gap between them. A racing test written for cycle 2
  detected the split in roughly four runs in five, took 7.5 to 14.5 seconds,
  and timed out under the two-second limit `[tool.mutmut]` passes — which the
  threshold script counts as inconclusive and fails on. It was withdrawn. This
  is the same shape as the finding Step 0 routed forward about
  `test_the_per_key_lock_table_survives_concurrent_creation`, and the same
  remedy applies: a fault-injection rendezvous inside the critical section,
  which forces every thread through it deterministically without a sleep.
  Step 8 owns building that mechanism once and applying it to both sites.

- **`close()` leaves a torn-down singleton resolvable (Step 8).** `close()`
  drains every built singleton and leaves the drained instances in the cache,
  so the next resolution hands one of them back with no error. Measured on
  `4e91736`: a singleton bound from a generator provider, resolved, then
  closed, reports `closed = True` and the following `di[Conn]` returns **the
  same object**. A caller that resolves after `close()` receives a closed
  connection and discovers it at the first call on it. `reset()`, added in
  Step 5 cycle 2, is the operation that drops the cache; `close()` deliberately
  does not, and the difference is documented — but nothing stops a resolution
  afterwards, and no error names the mistake. Step 8 owns deciding whether 1.0
  makes a container unusable after `close()`, raises a named error on a
  resolution that follows one, or keeps the current behaviour and documents it
  at the call site.

- **The mutation gate still flatters the two concurrency modules (Step 8).**
  The gate was cleared honestly just before Step 5 cycle 3, in a pull request of
  its own — 2358 killed and 55 survived of 2413, 97.7% — by pinning error
  messages as complete strings in `providers`, `decoration` and `typeguards`.
  Two modules were left alone on purpose. A
  local run of the same commit reports 17 survivors in `frozen` and 3 in
  `scope` where CI reports none, and those are the two slowest modules under
  mutmut's `--timeout=2`: on CI their tests exceed two seconds under a mutant,
  `pytest-timeout` fails them, and a failed test is what mutmut reads as a dead
  mutant. So CI is still scoring roughly twenty concurrency mutants as killed
  that a slower clock would show alive. Cycle 3 gave `test_resolution.py` the
  same per-module `timeout` marker cycles 2 used, which removed that distortion
  for the subprocess cases; the remaining two modules need the timeout question
  reopened rather than another marker, because they are where the fault
  injection item above also lands. Step 8 owns both together.

- **The seed contract is duplicated and never named (Step 8).** Three
  framework-free modules now declare the same callable shape by hand —
  `Callable[[X], tuple[ProviderKey, object] | None] | None` in `depin/ext/asgi.py`,
  `depin/ext/wsgi.py` and `depin/ext/cli.py` — together with the identical four
  lines that apply it, while `depin/ext/taskiq.py` seeds inline and honours the
  shape not at all. The duplicated lines are trivial; the duplicated *public type*
  is not. depin exports `ProviderKey` and `ScopeFrame` but never names the seed
  callable, so a third-party integration author has to re-derive the tuple
  protocol from three separate signatures. Naming it once in the contract and
  referencing it from all four modules is the one unifying move Step 5 had
  available and did not take. Step 8's surface review owns it, because adding a
  public alias is a contract change and the contract version is what Step 8
  freezes.

- **`Raises: TeardownError` is phrased as if it arrived bare (Step 8).**
  `depin/_core/scope.py` documents `TeardownError` as reported *inside* the
  raised `ExceptionGroup` rather than bare, but `depin/ext/wsgi.py`,
  `depin/ext/flask.py`, `depin/ext/cli.py` and `depin/_core/hosting.py` all list
  it under `Raises:` in a form that reads as a bare raise. A caller writing
  `except TeardownError` from that reading catches nothing. House-wide phrasing,
  inherited rather than introduced by any one cycle, and a docstring sweep rather
  than a code change. Step 8 owns it alongside the rest of the surface review.

## Step 6 — Consumer typing compatibility (0.17.0)

**Objective.** Make consumer-visible type inference a tested contract rather than
an assumption, before anything about the surface is frozen.

Taken from `specs/proposals/2026-08-31-multi-checker-consumer-typing-proposal.md`,
which records the decision and leaves the design open. The proposal's own handoff
order applies: a fresh five-checker baseline, then a reviewed design
specification, then a plan, then the implementation and its evidence.

**Why it precedes the freeze.** Step 8 justifies every symbol in `__all__` and
then commits to it. Freezing a surface before knowing whether five checkers agree
about it freezes in the dark: a promise that a generic survives, that an overload
resolves, or that an invalid call is rejected is only worth what the tools a
consumer actually runs will confirm. This step is also where
`provides=` cannot name a `Token` key is repaired, because that is a
consumer-typing defect and not a documentation one.

**Deliverables.** mypy, stock Pyright, basedpyright, ty and Pyrefly as blocking
gates over a consumer corpus checked against the **installed wheel**, not the
checkout; static type tests that separate exact-inference promises from
assignability promises; negative fixtures proving invalid uses stay invalid; and
a stated, bounded version policy with forward probing.

**Scope note.** The proposal was written on 2026-08-31, when the only integration
was `depin.ext.fastapi`. `depin/ext/` now holds twelve modules and the
distribution declares eight extras, several using PEP 695 generics — the ASGI and
WSGI middlewares, `install[C: CommandContext]`, and the `Inject[T]` alias. The
design owns deciding how much of that surface the consumer contract covers.

**Decision taken, measured rather than argued.** `Token[T]` declares a phantom
type parameter, and Pyrefly 1.2.0 infers it invariant where mypy, Pyright,
Basedpyright and ty infer it covariant — six errors in ordinary consumer code.
Eight remedies were measured against all five checkers over an installed-wheel
corpus (`specs/evidence/2026-09-01-token-variance-experiment.md`). Step 6 takes
**R4: a non-generic supertype in the eight `Token[object]` positions.** It clears
Pyrefly to zero on the consumer corpus at no cost to the public surface, and
`T` stays phantom.

The rejected alternative is worth recording. R5 adds a public
`payload(self, value: T) -> T` that pins `T` to an invariant use site, which
additionally makes all five reject `Container.value(Token[int], 'str')` — a real
false negative. It is refused on two grounds. The member returns what it receives
and has no runtime purpose, and its *shape was dictated by a checker*: it must be
public because Basedpyright's `reportUnusedFunction` fails the commit gate on a
private one. And the repair it buys is a side effect of invariance rather than a
designed constraint, so it regresses silently if the variance is ever revisited.
A member that exists to satisfy tool inference would not survive Step 8's surface
review honestly.

Four further remedies — a `TYPE_CHECKING` member returning `T`, a property, a
bare attribute annotation, and the legacy `TypeVar(covariant=True)` — clear
Pyrefly by *asserting covariance*, and Pyrefly caught the `value` false negative
precisely because it read `T` as invariant. They are trades, not wins.

Pyrefly is the non-conformant party: the typing spec's variance-inference
algorithm tests covariance first and a phantom parameter passes it. That is worth
reporting upstream, but a non-generic supertype sidesteps the question instead of
waiting on it.

**Risk.** Five blocking checkers is five upstream projects that can break the
build for reasons outside depin. Mitigation is the version policy: gates run
recorded versions, and a separate probe finds new releases before they are
adopted.

## Step 7 — Performance evidence (0.18.0)

**Objective.** Turn performance from an unstated property into measured, public,
reproducible evidence, and protect it with regression budgets that mean something.

Taken from
`specs/proposals/2026-08-31-performance-evidence-and-regression-proposal.md`,
under the same handoff discipline.

**Why here.** Step 8 already reserves the right to compile `ResolutionPlan` into
per-key closures "only on evidence", and to publish a comparison page. Neither is
possible without this step. It is also where the three algorithmic findings
earlier steps carried forward are settled — the cubic failing-freeze path, the
elision benchmark that elides nothing, and the exponential missing-key walk —
because each is a cost claim that should be measured before it is repaired.

**Deliverables.** Workload and claim contracts before measurement; semantic
equivalence proved between anything compared; direct-Python baselines as the
mandatory comparison; isolated, component, end-to-end and scaling tiers;
per-workload regression budgets justified by observed noise; and public raw
samples with reproduction instructions.

**Constraint the proposal fixes.** No aggregate "fastest library" claim.
Competitors appear only after passing eligibility, semantic-equivalence and
freshness rules, and an incomparable workload is labelled rather than counted as
a win. Unfavourable depin results stay visible under the same methodology.

## Step 8 — Surface freeze (0.19.0)

**Objective.** Settle the public surface and state what it commits to — without
yet claiming the number that makes it irrevocable.

**Deliverables.**

- Surface review: every symbol in `__all__` justified. Last window to remove or
  rename.
- `docs/stability.md`: the SemVer commitment, the deprecation window, what is
  public and what is not, and the Python version policy.
- Deprecation machinery: `DeprecationWarning` carrying its removal version, and
  a test that fails once that window expires.
- Revisit the `ty` job opened in Step 0: by this point Step 6 has decided its
  status, so what remains is recording the outcome.
- Gate the release workflow on the test suite before publishing. The pull
  request `release-please` opens carries no checks: GitHub does not start
  workflows from events raised by `GITHUB_TOKEN`, the same constraint
  `.github/workflows/release.yml` already documents in a comment on its
  `docs` job. `publish` therefore runs on the strength of `main` having been
  green at some earlier commit, not on its own verification.
- **Two under-constrained public signatures**, measured in Step 6's baseline and
  fixable only here because both repairs break the API. `FrozenContainer.override(Config, Other())`
  is accepted by all five checkers, and `Container.value(Token[int], 'str')` by
  four of five; in both, `T` appears in the key and the value parameter, so the
  solver widens it to the join. No change to `Token` reaches `override`, because
  `type[T]` is covariant by construction in the spec. A two-step
  `override[T](key).using(replacement)` was measured to make all five reject the
  invalid call while still accepting legitimate subclass widening; `value` has
  the same shape. This is the last window for either.
- The ten findings earlier steps routed here: the two scope-semantics gaps, the
  `close()` question, the captive-dependency message, a public `ProviderKey`
  renderer, the seed contract's missing public name, the `Raises: TeardownError`
  phrasing, the fault-injection mechanism, and the residual mutation-timeout
  inflation.

**Acceptance criteria.**

- No `TODO`, no undocumented public symbol, no feature flagged experimental.
- Every carried finding is closed or has a recorded decision not to close it.

## Step 9 — 1.0

**Undated, and deliberately so.** The preceding steps make 1.0 *possible*; none
of them obliges it. A version number is a support commitment, and the project
takes it when it chooses to, not because a roadmap reached its last row.

**What remains at that point** is only the acts of commitment, not engineering:

- `Development Status :: 5 - Production/Stable`.
- A comparison page against dishka, wireup, svcs and dependency-injector, built
  on Step 7's methodology and numbers.
- The stability document promoted from a statement of intent to a guarantee.

**Acceptance criteria.**

- The comparison page's numbers are reproducible from `benchmarks/`.
- Nothing in the public surface has changed since Step 8 without a recorded
  decision.

## Deliberately excluded

| Item | Reason |
| --- | --- |
| Python floor at 3.11 or 3.10 | Requires rewriting roughly 49 PEP 695 usages to `TypeVar` and revoking an `AGENTS.md` rule. 3.11 leaves support in October 2027. |
| Lazy injection (`Provider[T]`) | Primarily breaks cycles, which depin rejects by design; a singleton is already constructed on demand. |
| Assisted injection | An explicit factory plus `functools.partial` covers it at far lower surface cost. |
| Module-scanning auto-wiring | Conflicts with explicit `freeze()` validation and with the ban on import-time side effects. |
| Global container or `wiring` | Forbidden by `AGENTS.md`. |
| A broad in-repo integration catalogue | Each framework becomes permanent maintenance surface. The public contract transfers reach without transferring cost. |
