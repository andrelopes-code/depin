# Free-threading assumptions audit

This audit was run against CPython 3.13t and 3.14t with `Py_GIL_DISABLED=1`.
The runtime rules consulted are the [free-threading HOWTO](https://docs.python.org/3/howto/free-threading-python.html), [asyncio threading guidance](https://docs.python.org/3/library/asyncio-threading.html), [asyncio synchronization primitives](https://docs.python.org/3/library/asyncio-sync.html), and [Context Variables](https://docs.python.org/3/library/contextvars.html).

| Site | Shared state | Previous assumption | 3.13t / 3.14t finding | Disposition | Pinning test |
| --- | --- | --- | --- | --- | --- |
| `ScopeFrame._cache` | Cached singleton and scoped values | Dictionary check then insertion was effectively atomic | Both builds require the existing mutex around lookup/provide; reads and writes are protected | Retained mutex | `test_a_singleton_is_built_once_with_no_gil`, `test_scopes_stay_isolated_and_every_teardown_runs_with_no_gil` |
| `ScopeFrame._flights` | Unified per-key construction flights | Separate `_sync_locks` and `_async_flights` could arbitrate the same provider independently | Both builds require `_mutex` for lookup/create/remove; one `_Flight` serves sync callers, async tasks, and distinct event loops | Replaced both old tables with mutex-protected `_flights` | `test_the_unified_flight_table_survives_concurrent_creation`, `test_sync_and_async_resolution_share_one_flight`, `test_async_and_sync_resolution_share_one_flight` |
| `ScopeFrame._teardowns` | LIFO teardown list | Appends/drains did not race | Mutation occurs only under `_mutex`; drains detach one immutable tuple | Retained mutex | `test_scopes_stay_isolated_and_every_teardown_runs_with_no_gil`, `test_sync_close_preserves_independent_failures_in_lifo_order` |
| Sync and async single-flight | Cached construction across OS threads, tasks, and resolution entry points | The GIL or separate sync/async locks serialized every miss | One flight is selected before construction; all followers retry only after its exact completion | Retained `_Flight` with a per-flight mutex | `test_a_singleton_is_built_once_with_no_gil`, `test_sync_and_async_resolution_share_one_flight`, `test_async_and_sync_resolution_share_one_flight` |
| Async followers and executor starvation | Event-loop waiters | `asyncio.to_thread(event.wait)` leaves a worker available | A follower must not occupy the default executor: a one-worker executor otherwise deadlocks if the leader later uses `to_thread`; cancellation must also unregister the waiter | Per-loop futures are woken with `call_soon_threadsafe`, with no executor work | `test_async_follower_does_not_occupy_the_default_executor`, async failure/cancellation tests |
| Closed loops and reentrancy | Async waiter callbacks and inherited task context | One failed notification could hide live waiters; a task could await its own flight | Closed-loop waiters are abandoned without masking live waiter completion; an immutable `(ScopeFrame, cache_id)` ContextVar chain rejects self-joining | Notify every waiter independently; raise `CircularDependencyError` before joining own flight | `test_stale_and_duplicate_flight_completion_do_not_signal_replacement`, `test_sync_self_resolution_raises_instead_of_waiting_for_its_own_flight`, `test_async_child_task_self_resolution_raises_instead_of_waiting` |
| `threading.Lock` and awaits | Frame and flight mutexes versus event loop | Holding an OS lock through await was harmless | It can block unrelated threads/loops; `_mutex` only selects/removes flights and a flight mutex only changes waiter state | No OS lock is held across provider construction or await | `test_async_singleton_is_single_flight_across_event_loops` |
| Scope `ContextVar` | Active frame in sibling tasks, sibling threads, and child threads | Context always follows a new thread | Sibling tasks inherit the active frame. Child-thread inheritance is controlled by the build's `thread_inherit_context` setting, so the test accepts and records a consistent inherited or isolated child context; worker scopes are always explicit | Context-local API retained | `test_scope_context_is_explicit_in_child_threads_and_inherited_by_sibling_tasks`, `test_scopes_stay_isolated_and_every_teardown_runs_with_no_gil` |
| Override `ContextVar` stack | Override inheritance/isolation in sibling tasks and child threads | Overrides were process-global | Sibling tasks inherit the override. Child threads consistently receive the inherited override or the unoverridden provider according to their context-inheritance setting | Context-local stack retained | `test_override_context_isolated_or_inherited_by_child_threads`, `tests/unit/test_overrides.py` |
| Graph/build structures | Dictionaries/lists while building a plan | Freeze structures might be concurrently mutated | They are call-local during freeze and not retained mutable after it returns | No shared state | `tests/unit/test_graph_properties.py` |
| `ResolutionPlan` | Post-freeze provider map/order | Readers needed a lock | Frozen plan data is immutable and only read after construction | Immutable reads retained | `tests/unit/test_container.py` |
| Missing-provider suggestions | `sys.modules` and module namespaces | Module dictionaries are stable while inspected | Snapshots are taken before searching; no shared depin mutation is retained | Snapshot reads retained | `tests/unit/test_errors.py` |
| FastAPI extension | Container `ContextVar` | Request container leaked across requests | ContextVar is request/task-local; integration opens an explicit async scope | Context-local integration retained | `tests/integration/test_fastapi.py` |
| Step 0 `gc.get_objects()` | Interpreter heap enumeration | GIL made heap walking a valid verification source | Removed before this step; free-threaded correctness is now demonstrated through public behavior | Historical only; no live code | `specs/evidence/2026-08-30-step-0-baseline.md` |

The cross-loop stress test uses 32 OS threads and one `asyncio.run` loop per thread. The one-loop tests additionally prove that a failed or cancelled leader removes and signals its exact flight, so a causally registered follower can construct rather than wait forever.
